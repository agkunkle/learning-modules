Why this module

Every program that Linux runs starts as a file in ELF format. Compilers, linkers, the kernel and the dynamic linker all read the same file. Each one reads a different part of it.

In this module you follow one very small 64-bit Arm (AArch64) program. You start with the bytes in its file. You end with the memory of a running process.

We built the examples with the GNU assembler and linker. We never run them. We only read them with readelf and objdump. You do not need Arm hardware.

How to read the numbers

Every address, offset and size comes from the real example files, unless a label says illustrative. Two things are illustrative: the page size (4 KiB in the clips) and the load bias B of the position-independent example.

Recognize an ELF file

An ELF file starts with the ELF header. In ELF64 it is 64 bytes long. It always sits at offset 0. It tells a reader what kind of file this is, and where to find the rest.

Three fields identify the file. They answer three different questions:

  • EI_CLASS: how big are the structures (32-bit or 64-bit layout)?
  • EI_DATA: which byte order do multi-byte fields use?
  • e_machine: which CPU architecture is the code for?

Here is the same header, as readelf -h prints it. Press Next to walk through it.

ELF64 does not mean AArch64

x86-64 files are ELF64 too. The CPU is named by e_machine (183 for AArch64). AArch64 files are also not always little endian: the Arm ABI allows both byte orders. This module uses little-endian examples.

Two views of one file

An ELF file has two tables. Both describe ranges of the same bytes. They serve two different readers.

  • Sections are the link-time view. A linker combines sections from many files.
  • Segments are the execution view. The system uses them to build a process image.

The gABI says it directly: a section header table is required for files used during linking, and optional for files used to create a process image. For the program header table, it is the other way round.

A segment is not a section

In this small file, each segment holds one or two sections. A larger file can put many sections into one segment. Do not expect one section per segment.

Map bytes into memory

The next clip is the core of this module. It follows demo.elf from the program header table to three mappings in process memory. Press play, or drag the bar to look at one moment.

The clip used one rule. For a byte at file offset off inside a PT_LOAD segment:

address = load_bias + p_vaddr + (off - p_offset)

The range of valid offsets is p_offset up to, but not including, p_offset + p_filesz. For demo.elf the load bias is 0, because the file type is EXEC (fixed addresses).

The linker also keeps p_offset and p_vaddr equal modulo p_align. Check LOAD 2: 0x108 and 0x410108 differ by 0x410000, a multiple of 0x10000. The kernel works in whole pages, so it needs the same match modulo the page size.

The kernel code

Linux v6.12 maps a segment in two functions. elf_map maps the file bytes. It rounds the start down and the size up to whole pages.

elf_load then deals with the zero tail. It zeroes the rest of the last file page and adds anonymous zero pages for the rest.

The permissions come from p_flags:

.bss is not a segment

.bss is a section of type NOBITS. It lives in the zero-filled tail of the writable segment, where p_memsz is larger than p_filesz.

Virtual memory, not RAM

A mapping is a range of virtual addresses. The kernel fills physical pages when the program uses them. The clip assumed 4 KiB pages. Linux on arm64 can be built with 4, 16 or 64 KiB pages: a program reads the real value from AT_PAGESZ.

Follow program startup

Mapping the segments is only the first stage. Three different parts of the system share the work before your main runs:

  1. The kernel maps the segments, builds the stack and starts the first user instruction.
  2. The dynamic linker (the "interpreter") loads libraries and applies relocations.
  3. The startup code in the program and in libc sets up the C runtime and calls main.

Read symbols and AArch64 relocations

The adrp page is always 4 KiB in the relocation formulas, even when the kernel uses larger pages. The two kinds of relocation differ in who applies them and when:

  • Static relocations are in relocatable objects (ET_REL). The linker applies them. A finished executable has none left.
  • Dynamic relocations are in executables and shared objects. The dynamic linker applies them at load time. R_AARCH64_RELATIVE, R_AARCH64_JUMP_SLOT and R_AARCH64_GLOB_DAT are the common ones. Our example has the first two.

Understand PIE and shared libraries

An ET_EXEC file asks for fixed addresses. A position-independent executable (PIE) and a shared library are ET_DYN files. They start at address 0 in the file and are loaded at a load bias: the difference between the runtime address and the address in the file.

Inspect without executing

readelf reads a file. It does not run it. That is why you can use it on any file, for any architecture, on any machine. A good order:

  1. readelf -h: what is this file? (class, data, machine, type, entry)
  2. readelf -l: how is it loaded? (segments, flags, FileSiz and MemSiz, interpreter)
  3. readelf -S: what are the link-time pieces? (sections)
  4. readelf -d: what does it need? (NEEDED libraries, flags)
  5. readelf -r: what must still be fixed? (relocations)
  6. readelf -s: which names does it have? (symbols)
QuestionCommandLook for
Is it AArch64? Is it a PIE?readelf -h Machine, Type, Entry point
Is some memory zero-filled?readelf -l FileSiz smaller than MemSiz
Which libraries does it need?readelf -d NEEDED
Is a call resolved?readelf -s and -r UND symbols, R_AARCH64_* entries

Practice with the outputs you have already seen. In demo.elf, the program headers show the zero tail (LOAD 3). In dyn.elf, the dynamic section shows the library (libstub.so) and the relocation table shows the two fixups.

The symbols of the linked file show that the call now resolves: helper has an address, and _start sits at the entry point.

Diagnose common surprises

Three things often look wrong at first. None of them breaks the basic model.

Case 1: there are no sections

We made a copy of demo.elf and zeroed the section-table fields of its header (e_shoff, e_shnum, e_shstrndx). We did not run it.

The load information is complete. Only the link-time names are gone.

Case 2: the file is stripped

We ran strip on another copy. The symbol table is gone. readelf -s printed nothing for this static file. The program headers did not change.

A stripped file can still run, but a debugger cannot name its functions. Do not generalise: this example has no dynamic symbols. Files with dynamic linking keep the ones they need.

Case 3: the entry point is not main

Look again at the symbols of demo.elf (section 7). The entry point is 0x4000e8. The symbol at that address is _start. This example has no main.

A short checklist

  1. Missing names (sections, symbols)? Check the load information in readelf -l before you decide the file is broken.
  2. Strange start? Read Entry point and look up that address in the symbols.
  3. Wrong platform? Check Machine, then Class and Data.
  4. Not sure what it needs? Read the dynamic section. Do not run the file to find out.
